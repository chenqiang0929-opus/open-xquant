## 1. R09 正式因子口径与案例表勘误

### 1.1 正式 R09 四因子

正式 R09 核心质量复合包含四项：

1. `net_profit_margin_ttm`：先把累计季度值还原为单季度，再滚动四个季度求和，`net_income_ttm / revenue_ttm`。
2. `roe_level`：观察日可用的最新披露 ROE。
3. `roe_change_yoy`：当前 ROE 减去四个报告期之前的 ROE。
4. `cash_conversion_ttm`：`operating_cash_flow_ttm / net_income_ttm`。

财务数据在**公告日之后的第一个交易日**生效，禁止用未来报告回填。

正式来源：

- `formal-validation-r09-clean/versions/v001/01_brainstorm/strategy_idea_brief.json`
- `codex-notes/R09-阶段性回测总结.md`
- `tools/evaluate_quality_factors.py`

### 1.2 正式横截面池

因子面板的日级可交易过滤为：

```text
非 ST
非停牌
非涨停（用于下一交易日买入可执行性）
上市交易日数 >= 250
volume > 0
```

市场范围是沪深 A 股历史时点股票池，排除 B 股和北交所，保留退市股票的历史可交易区间；基础缓存共 5,217 只。

### 1.3 各因子的 eligibility

正式实现不是对所有非空财务值直接排名，而是：

```text
TTM净利率：net_profit_margin_ttm > 0
ROE水平：roe_level > 0
ROE同比变化：公司当期 ep_ttm_pit > 0
现金利润转换：ep_ttm_pit > 0 且 cfp_ttm_pit > 0 且 cash_conversion_ttm > 0
```

四因子复合要求四项排名全部存在，使用 `mean(..., skipna=False)`；任意一项缺失则核心复合分缺失，不按剩余因子平均，也不填零。

### 1.4 缩尾、分位和综合分顺序

确切顺序是：

```text
先应用各因子的 eligibility
→ 对该因子当日有效横截面计算 1%/99% 分位点
→ 将原值 clip 到 1%/99% 边界
→ 对缩尾后的数值做升序百分位排名
→ 四个百分位等权平均
```

低应计因子是先缩尾，再取相反数排名；它不属于核心四因子。

### 1.5 “高/中/低”不是正式 R09 规则

你从 276 行案例反解出的切点是正确的：

```text
核心质量分 >= 0.70：高
0.30 <= 核心质量分 < 0.70：中
核心质量分 < 0.30：低
核心质量分缺失：缺失
```

但是，这组切点只是 `build_four_stock_case_data.py` 为 Excel 展示临时增加的**数值分层**。正式 R09 只定义连续质量分、横截面排名和 Top20 组合，没有确认“高/中/低”三档。

因此模板字典中“按 R09 质量排名分层”表述不够准确，应改成：

> 案例展示分层：按核心质量分的固定数值切点 0.30/0.70 分档；不属于正式 R09 选股门槛。

### 1.6 为什么案例质量分与你不同

案例生成器读取 `data/features/quality_panels/panel_5d.parquet`，取不晚于观察日的最近一个五日面板，但随后直接对原始六个质量字段做 `rank(pct=True)`：

- 没有重新应用正式 R09 的四项 eligibility；
- 没有执行正式 `winsor_rank()`；
- 使用最近五日面板，而不是每个观察日重新构建正式截面；
- 虽然使用 `skipna=False`，但无效的负值或不合格值仍可能参与单项排名。

所以案例工作簿中“严格复用 R09 冻结口径”的说明是错误的。你发现 600066 在你侧缺失、案例侧有值，正是这个问题的证据。

**处理决定**：你的 2022 表中质量等级暂不与案例表强行对齐。应使用 `tools/evaluate_quality_factors.py::factor_scores()` 的正式 eligibility 和 `winsor_rank()` 重算；案例表质量列后续也应按该函数重建。

## 2. 周线结构五态的确切实现

### 2.1 正式 X01 只有二元辅助状态

`x01_price_start_v1.0.0.json` 正式定义只有：

```text
weekly_close > weekly_ma20 > weekly_ma60
```

它是 `binary_auxiliary`，`hard_gate=false`，不会改变正式价格信号。

五态“多头趋势 / 突破启动 / 回踩修复 / 均线蓄势 / 弱势结构”是案例生成器中的辅助解释标签，不是 v1.0 正式规则；`X01_600输出字段规范_v1.1草案.md` 也没有给出五态判别式。因此案例字段字典把五态来源写成“X01 v1.1草案”是不准确的。

### 2.2 案例生成器的真实五态判别顺序

实际代码按以下顺序执行，先命中的状态优先：

```text
未知：MA20周或MA60周缺失

多头趋势：weekly_close > weekly_ma20 > weekly_ma60

突破启动：weekly_close >= weekly_ma20 且 日线ret_5 > 5%

回踩修复：weekly_close >= 0.95 * weekly_ma60
          且 weekly_close < weekly_ma20

均线蓄势：abs(weekly_close / weekly_ma20 - 1) <= 5%

弱势结构：其余情况
```

这与你反解的版本有两个关键差异：

1. “突破启动”还要求日线 `ret_5 > 5%`，并不要求 `MA20周 <= MA60周`。
2. “回踩修复”要求周收盘不低于 MA60周的 95%，而不是只判断 `MA20周 > MA60周`。

### 2.3 周边界与前视处理

周线使用日线重采样：

```text
W-FRI
周收盘 = 该周最后一个可用日收盘
```

然后选择 `周标签日期 <= 观察日` 的最后一行：

- 周一至周四观察：使用上一已完成周；
- 周五收盘观察：使用截至该周五收盘的当周；
- 不使用观察日之后的数据。

如果你的实现统一排除观察日所在周，即使观察日是周五，也会产生系统差异。复现案例时请采用“周五收盘后当周已完成”的口径。

### 2.4 处理决定

你可以按上述代码复现案例，但请在输出中把它命名为“案例周线辅助标签”，不要称为正式 X01 周线规则。正式字段应另保留二元 `weekly_bull_alignment_flag`。

## 3. 平台缩量比、收敛比和触线日

### 3.1 案例生成器确实要求 MA100 向上

触线日定义为最近强势日之后第一个同时满足以下条件的交易日：

```text
low[k] <= MA100[k] * 1.03
MA100[k] > MA100[k-20]
```

其中 MA100 日线作为约 20 周线的近似。

宇通客车 2023-09-28 案例的计算是：

```text
最近强势日 ts：2023-07-20
首次触线日 td：2023-08-11
2023-08-11 low：10.704895
2023-08-11 MA100：10.515752
low / MA100：1.017987，低于 1.03
MA100 相对 20 个交易日前斜率：+7.775%
```

因此在案例数据源上，2023-08-11 同时满足触线和 MA100 向上；2023-09-28 可以计算三项平台值。你侧为 NaN，说明双方的 `low`、MA100 输入序列或触线搜索边界仍不同。请优先对照上述五个数值，而不要从最终平台状态反推。

### 3.2 TR 使用真实波幅

案例生成器使用：

```text
TR[t] = max(
    high[t] - low[t],
    abs(high[t] - close[t-1]),
    abs(low[t] - close[t-1])
)
```

包含跳空，不是收盘收益波动率。

### 3.3 窗口端点

案例生成器的窗口为：

```text
平台深度 = 1 - min(low[ts:t]) / max(high[ts:t])

平台缩量比 = mean(volume[ts:t])
             / mean(volume[max(0, ts-60):ts-1])

平台收敛比 = mean(TR[td:t])
             / mean(TR[max(0, ts-60):ts-1])
```

按 Python 切片说明：平台窗口包含 `ts` 和观察日 `t`；强势日前窗口包含最多 60 个交易日，但不包含 `ts`；TR 分子包含 `td` 和观察日。

### 3.4 案例平台数据是混合来源，需要特别说明

四股案例不是单一平台引擎的纯输出：

- 月末观察行由 `build_four_stock_case_data.py::platform_daily()` 重算；
- 如果某日存在于你的 `platform_buypoints.csv`，案例生成器会用该 CSV 覆盖平台突破事件字段；
- 因此案例只适合字段展示和锚点核对，不适合反向定义唯一的正式平台算法。

你的 `platform_buypoints.csv` 和 `platform_pivot.py` 对平台专项研究的来源优先级高于这份案例辅助生成器。案例表中 271/272 的一致已经足够说明大框架相同；宇通 2023-09-28 应保留为数据输入/搜索边界专项差异，不应强行修改成一致。

### 3.5 胜宏科技 2023-09-12 的假突破补充

该日按旧规则确实突破前一日平台上沿，但事后检查表明它是典型假突破：突破日 RPS60 已降至 29.95、收盘仅位于当日振幅约 50.7%、上影线约 8.7%，次日收盘重新跌回平台上沿下方；后 20/60 日分别约 -16.45%/-19.26%。

这不用于修改历史标签，但说明平台信号仍只能保持 `WATCHLIST`。下一版应独立验证以下辅助过滤，而不能直接回填旧结果：突破日当前 RPS、收盘位置、上影线、平台最短持续期、次日/两日确认。

## 4. 成交量是否随前复权调整

明确答案：**没有。**

`tools/build_qfq_market.py` 的处理是：

```text
qfq_price = raw_price * adj_factor / latest_valid_adj_factor
```

只调整 `open/high/low/close`；`volume` 原样保留。manifest 也只把 OHLC 列为 `adjusted_columns`。

因此复现案例平台缩量比时，应直接使用 `data/market_rps_qfq/*.parquet` 中保存的原始成交量，不要乘除复权因子。你若对成交量做了拆并股反向调整，会与案例值产生系统差异，宁德时代 2026 年的偏差很可能来自这里。

这不代表“原始成交量永远是更优研究口径”。遇到拆股、送转和股本变化时，原始成交量可比性本身需要专项验证；当前回答只说明案例和现有缓存的真实实现。

## 6. RPS 横截面池的确切实现

`tools/precompute_rps_cache.py` 的实现是：

```text
价格：hfq_close
收益：hfq_close / hfq_close.shift(N) - 1
横截面：策略 spec 中的 5,217 只股票，当日 N 日收益可计算者
排名：rank(axis=1, pct=True, method="average") * 100
最低横截面样本数：100
510300：写入缓存，但不参加股票 RPS 排名
```

RPS 预计算步骤本身没有逐日增加 `not_ST / not_suspended / volume>0` 过滤；这些限制在后续候选或交易可执行性环节处理。因此你使用“非停牌且有成交”的池子虽然数值非常接近，但不是字节级相同口径。

`codex_template_2022.csv` 可以保留，当前建议分三层处理：

1. **可直接保留**：X01 信号类型、统一信号、RPS、距高低点、MA20持续度等已对齐字段。
